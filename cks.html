Question 1 of 12 · Cluster Setup
A company needs pods in namespace 'finance' to accept ingress traffic ONLY from pods labeled role=reporting that live in namespace 'analytics'. All other ingress traffic to 'finance' pods must be blocked. Which NetworkPolicy correctly implements this?
Placing namespaceSelector and podSelector inside the SAME 'from' list item ANDs them together — traffic is only allowed if the source pod matches BOTH conditions (in analytics namespace AND labeled role=reporting). policyTypes: [Ingress] with an empty podSelector applies the policy to all pods in 'finance' and defaults to deny-all-ingress except what's explicitly allowed.
Question 2 of 12 · Cluster Hardening
A security team wants pods running in the "default" namespace to stop automatically receiving a mounted service account token unless a workload explicitly requires API access. Which approach correctly enforces this while keeping the cluster functional?
Setting automountServiceAccountToken: false on the ServiceAccount (or overriding it per-Pod) is the supported mechanism to stop the API server credentials and CA bundle from being auto-mounted into pods that don't need them, satisfying least privilege without breaking scheduling.
Question 3 of 12 · System Hardening
A security engineer must restrict a Pod named 'payment-api' so that it runs with a custom AppArmor profile named 'k8s-payment-restrict' that has already been loaded on every node. Which configuration correctly enforces this in a cluster running Kubernetes 1.30+?
Since Kubernetes 1.30 (GA), AppArmor is configured natively via the container's securityContext.appArmorProfile field, with type Localhost and localhostProfile pointing to the profile name already loaded on the node. This replaced the older beta annotation approach.
Question 4 of 12 · Minimize Microservice Vulnerabilities
A platform team wants to enforce the 'restricted' Pod Security Standard on the 'payments' namespace without deploying any third-party admission controller, while first auditing violations before full enforcement. Which solution BEST meets these requirements?
The built-in Pod Security Admission (PSA) controller supports independent audit, warn, and enforce modes via namespace labels. Staging audit/warn before enforce lets teams find violations without breaking running workloads, and this requires no third-party controller.
Question 5 of 12 · Supply Chain Security
A company wants to minimize the attack surface of container images used in its Kubernetes cluster. The current base images use full Ubuntu with a shell, package manager, and many unused utilities. The application is not statically compiled and still requires a minimal runtime. Which approach BEST reduces the attack surface while keeping the application functional?
Distroless images remove the shell, package manager, and unnecessary OS utilities while still including only the minimal runtime dependencies needed to execute the application, directly reducing the attack surface without breaking functionality.
Question 6 of 12 · Monitoring, Logging, and Runtime Security
A security team suspects an attacker has gained a foothold in a production pod and is attempting to open an interactive shell to explore the filesystem. They want real-time detection of this specific behavior across the cluster using syscall-level visibility, without modifying application code. Which solution BEST meets this requirement?
Falco hooks into syscalls (via kernel module or eBPF probe) and ships a default rule, 'Terminal shell in container spawned', that fires when a shell process (bash, sh, etc.) is spawned inside a container, exactly the real-time behavioral detection required here.
Question 7 of 12 · Cluster Setup
kube-bench reports FAIL for etcd check '2.2 Ensure that the --client-cert-auth argument is set to true'. Which change to the etcd static pod manifest remediates this finding?
'--client-cert-auth=true' forces etcd to require and validate client certificates for client-to-server (API server-to-etcd) connections, which is exactly what CIS benchmark check 2.2 tests. Without it, etcd may accept unauthenticated client connections even if TLS certs are configured.
Question 8 of 12 · Cluster Hardening
You must configure the kube-apiserver so that it rejects all unauthenticated (anonymous) requests, forcing every client to present valid credentials. Which flag directly accomplishes this?
--anonymous-auth=false disables the system:anonymous user and system:unauthenticated group, so every request must pass an authentication method (client cert, token, etc.) before authorization is even evaluated.
Question 9 of 12 · System Hardening
A container in a cluster must be prevented from making any syscall not explicitly allowed by a custom JSON profile stored at /var/lib/kubelet/seccomp/profiles/audit.json on each node. Which securityContext configuration achieves this?
type: Localhost tells the kubelet to load a custom profile, and localhostProfile gives the path relative to the kubelet's seccomp root directory (/var/lib/kubelet/seccomp/), so profiles/audit.json resolves to the file described in the scenario.
Question 10 of 12 · Minimize Microservice Vulnerabilities
A team must run an untrusted, multi-tenant workload requiring isolation via a user-space kernel that intercepts and emulates syscalls, while remaining compatible with the existing containerd CRI shim v2 interface. Which solution BEST fits?
gVisor implements a user-space kernel (Sentry) that intercepts application syscalls before they reach the host kernel, integrates via containerd's runtime shim v2, and is designed specifically for this isolation model.
Question 11 of 12 · Supply Chain Security
A security engineer wants to run static analysis directly on Dockerfiles before the image is built, flagging issues such as running as root, using ADD instead of COPY, and missing a USER instruction. Which tool is purpose-built for this task?
hadolint is a dedicated Dockerfile linter that parses Dockerfile instructions and flags best-practice violations such as missing USER directives, use of ADD, and root execution, before any image is built.
Question 12 of 12 · Monitoring, Logging, and Runtime Security
You need to configure a Kubernetes audit policy so that requests to read Secrets are logged in full detail (including request and response bodies) for forensic purposes, while routine 'list pods' requests are logged with metadata only to save storage. Which audit level should be assigned to the Secrets rule?
The RequestResponse level logs the full event metadata plus the request and response bodies, which is required to capture exactly what Secret data was accessed or returned — necessary for forensic review of sensitive resource access.
